## Notes for next session: design brief

_Not a punch list. This is a working design doc lemon + the agent iterate
against for the polish/direction pass. Approach it as a UI designer: name
the actual problem, weigh options with tradeoffs, then implement: not
"apply corrections in order." Goal is a **unique but readable + fun**
event UI, not a beautified admin panel._

### Design principles for this pass

- **Hierarchy over density.** If everything on a card looks equally
  important, nothing is. Establish primary/secondary/tertiary weight before
  removing content. A single dominant piece + calm supporting metadata
  reads more information-dense than nine equally-weighted pills.
- **Voice per surface, not everywhere.** The noir typewriter voice is a
  spice, not a base. It works LOUD in captions, headings, and stamps.
  Silence between those beats is where the design breathes. Body copy,
  buttons, and stats can stay neutral: they don't need to be noir too.
- **Design for the moment that matters most.** For each page ask: what's
  the ONE action or piece of information the user is here for? Design
  that first at 100% weight; everything else supports at 50-70%.
- **Repeated visual language for repeated concepts.** Difficulty is
  ALWAYS shown the same way. Payouts always look the same. Attacks
  always feel the same. Don't reach for a new treatment per new concept.
- **Unique doesn't mean loud.** Noir cards can be quiet. A single
  well-placed stamp on a completed step is more distinctive than three
  badges + a border + halftone. Restraint is a design choice.

### Problem 1: cluttered / busy pages, badge sprawl

**The actual issue:** every metadata attribute (length, difficulty, v1,
one-shot, status, crew color) currently wears the same visual weight: a
pastel `<Badge>` pill. Cards look like they were generated by a form
builder, not designed. The typewriter accent gets drowned out.

**Design principle at play:** hierarchy + repeated visual language.

**Directions to weigh:**

1. **Strip badges, promote typography.** Length/difficulty become part of
   the card's TITLE region (small letter-spaced type above the contract
   name: like a chapter marker). Status stays as a badge but redesigned.
   Result: fewer discrete objects per card, calmer read.

2. **"Case-file" tag system.** Replace pastel Chakra pills with a custom
   `<CaseFileTag>` component: typewriter mono, hairline border, no fill,
   uppercase, letter-spaced. Only used where genuinely needed (state
   change, one-shot-used, attack applied). Everything decorative becomes
   inline text.

3. **Stamp-first state indication.** Repurpose the noir stamp component
   for state that's already earned (COMPLETED, BURNED, TAKEN, ALIBI USED)
   because high-drama moments deserve the stamp. Pending/available state stays
   quieter: a colored ink dot next to the label, or nothing at all.

**Recommendation:** combo of 2 + 3. Kill pastel badges entirely. Every
metadata attribute has a designed treatment or doesn't appear.

**Specific offenders to prune:**

- Length + difficulty pills on every contract card + step row
- "v1", "one-shot" chips in the market catalog
- Step-status colored badges (LOCKED/UNLOCKED/SUBMITTED/COMPLETE): most
  can be inline typography or a leading ink dot instead
- Difficulty tag on task pool cards in the playground
- Redundant Chakra Badges that repeat info already in the card header

### Problem 2: role / phase labels don't read

**The actual issue:** `SCOUT / MUSCLE / FENCE` (step role) and `CASE /
STEAL / LAUNDER` (step phase) were designed as narrative flavor. In the
current UI they render as unadorned pastel tags without context: they
add noise, not story.

**Design principle at play:** voice per surface. Narrative flavor belongs
where narration is expected (feed copy, event log, discord posts). Cards
should be functional.

**Directions to weigh:**

1. **Drop from card UI, promote in feed.** Steps show just ordinal + task
   ("2. Kill 40 Zulrahs"). The narrator picks up the flavor: _"The
   Ironclads have their fence lined up for the Zulrah drop-off. Payday
   incoming."_ Card stays clean, story shows up where players read it.

2. **Lean in as a "role" motif: one per contract, not one per step.**
   The contract has an assigned role (SCOUT contract, MUSCLE contract),
   giving it flavor + strategic identity. Steps stay ordinal. Feels
   more like a "kind of job" than a taxonomy per step.

3. **Rename to less-jargony verbs.** `Case / Steal / Launder` → maybe
   `Setup / Score / Getaway`? Less genre-specific but still narrative.
   Still a card-level tag though: doesn't fix the density problem.

**Recommendation:** option 1. Drop from cards, lean into feed. Simplest,
highest-payoff. Server data can stay as-is; just don't render it on the
card. If we ever want it back, easy retro-fit.

### Problem 3: contract names are formulaic

**The actual issue:** current generator is `The {firstStepDisplayName}
{suffix}`: mechanically produced, feels stiff, betrays the algorithm.
"The Wintertodt Job" reads like a placeholder.

**Design principle at play:** unique moments earned by variety +
specificity. A name should feel like it _belongs_ to the crew that pulled
it.

**Directions to weigh:**

1. **Curated seeded pool of noir-flavored templates**, indexed by
   length/difficulty. Small pool (~30-60 names per tier), rotated with
   seed. Templates can include location noir names (`The Ardougne Score`,
   `Midnight at Chambers`), day-of-week noir (`Tuesday at the Corp`),
   codename noir (`Operation Cold Storage`), and mood noir (`Cold Case:
Zulrah`). Lets us mix flavors so a batch feels varied.

2. **Composed names using step content + verbs.** i.e. `Getting Made
at the Barrows`, `Cracking the Wintertodt Payroll`. Programmatic but
   with better templates. Still risks feeling generated.

3. **Curated pool with occasional composed variety.** Best of both.

**Recommendation:** option 3. Start with a hand-curated pool of ~50-100
noir names indexed by tier; salt in ~15% composed names for variety. All
lives in `skulduggeryContractNames.js` alongside the task pool. Weight
toward curated at first, iterate as we see what plays well.

Also worth: **name should hint at length + difficulty subtly**: heist
names shorter/snappier, kingpin names longer/more grandiose. Reader
should feel the weight.

### Problem 4: raw numbers (KC / XP)

**The actual issue:** raw integers everywhere. `metricTarget: 1500000
xp` breaks the typewriter voice: you'd never write that on a case file.

**Design principle at play:** typography scales, and numbers deserve
typographic treatment. Big numbers in display type, small qualifier text
below. Abbreviate large values.

**Direction:** copy Battleship's `formatMetric` helper (check
`client/src/utils/battleshipHelpers` or wherever it lives). Apply to:
event page step targets, shakedown task labels, task pool browser,
contract previews. Prices + cut balances too: `500 cut` reads fine but
`1,250,000 cut` should be `1.25M`.

Also worth: **remove redundant unit labels where context makes it
obvious.** `250 kills` reads better than `boss_kc target: 250 kc`. Steps
know their metric type: the label should be contextual, not stamped
onto every value.

### Problem 5: task pool + registry data pass (design-adjacent, not code)

Lemon wants to review what actually shows up as steps. Two data surfaces:

- `server/utils/skulduggery/skulduggeryContent.js`: difficulty overrides
  for registry entries. Currently classifies bosses by category (short =
  easy, medium = intermediate, long = hard). Some manual overrides.
  Worth a review pass for edge cases + preferences.
- `server/utils/skulduggery/skulduggeryTaskPool.js`: the 13 curated
  thieving tasks. Volume + variety could grow. Also worth reviewing
  metric types + targets.
- **Shakedown tasks specifically need a closer look.** The pool doubles
  as the "race" tasks a shakedown attacker + victim run in parallel,
  which means the pool needs to be small enough to be repeatable but
  varied enough to keep races interesting, and every entry needs to be
  timeable + verifiable enough to survive the timestamp-winner resolution.
  Some entries in `skulduggeryTaskPool.js` were sized for step usage,
  not race usage: worth a pass to make sure shakedown targets are
  short + punchy (a race that takes 4 hours is not a race).

Not urgent, but flagged for a design/content session with lemon at the
helm.

### Design opportunities I'd flag as a designer (lemon hasn't called out)

- **Event page has no dominant primary.** For a crew mid-contract, the
  primary action is: submit proof for your current unlocked step. That
  should be the LOUDEST thing on the page: big display target, one
  prominent submit surface. Everything else (feed, market, board) is
  context. Right now it all sits at ~equal weight.
- **Step chain deserves a visual metaphor.** Currently a list of step
  rows. Could actually feel like a chain: comic-panel gutters between
  steps, or connecting lines, or a fill-in progress meter along the
  side. Reinforces the "chained contract" concept.
- **Market panel reads as an admin form.** It's supposed to feel like
  a shady menu you order from. A single anchor illustration (silhouette
  fedora fence, or a hand-lettered "the fixer" chalkboard header)
  transforms the feel without requiring more art per action.
- **Feed hierarchy is flat.** Every kind wears the same yellow caption
  box. The dramatic ones (SHAKEDOWN, HEAT, KINGPIN unlock, CONTRACT
  BURNED) should feel bigger: maybe wider caption boxes, colored
  borders, or splash-panel treatment. Routine "pull/complete" stay
  small.
- **State transitions have no moment.** Completing a step, buying
  reputation, winning a shakedown: these are the fun parts. Right now
  they update quietly. The stamp fx exists but isn't animated in;
  wiring an ink-slam animation on state change would sell the game
  feel. Respect `prefers-reduced-motion`.
- **Two voices, one type treatment.** The narrator ("The fixer is
  holding the temple job off the streets…") and the mechanic labels
  ("cutBalance: 500") currently look the same. Different characters →
  different type treatments. Narrator gets serif italic caption boxes
  (this is already done); mechanic labels should stay neutral mono
  - calm.
- **Densely-detailed vs calm mode.** Different players want different
  info surfaces. Long-term, might be worth a toggle: dense-dashboard
  vs chapter-book. Not v1, but flag for future.

### Things to leave alone this pass

- Server invariants, mutation transactions, ledger flow, race
  resolution: all tested + working. Display pass shouldn't touch them.
- Base palette + font choices in `noir.js` after the v3 pass (dark
  cool charcoal, cream paper, brass gold, blood red, Special Elite
  - Poppins + Georgia + IBM Plex Mono). Palette can add tokens as
    needed; don't rehash the base direction.
- `HalftoneAccent` implementation (inline SVG w/ radial-gradient mask)
  is dialed. Consumers can tweak params; the primitive is done.
- Playground page STRUCTURE (Palette / Typography / Components /
  Feed Voice / Generator / Payout Ladder / Market / Task Pool /
  Contract Previews). Iterate contents inside those sections; don't
  add new top-level sections without discussing.

### Problem 6: dashboard + create page are naked

**The actual issue:** the /skulduggery landing (`SkulduggeryDashboard.jsx`)
and /skulduggery/create (`SkulduggeryCreatePage.jsx`) are stock Chakra
scaffolding: no noir palette, no typography voice, no halftone, no
sectioned setup surface, no personality. Both surfaces are the very first
thing a coordinator + player see when they click into the mode, and they
currently pitch the wrong feeling. **These two pages deserve the utmost
care.**

**Design principle at play:** first impressions. If the entrance to the
event doesn't look like Skulduggery, nothing else that follows earns
credibility. And the setup surface is where a coordinator lives when
they're building the event: it needs to feel intentional, not like a
tax form.

**Direction: dashboard (`/skulduggery`):**

- Full noir shell (dark ink bg, cream paper text, IBM Plex Mono for
  metadata, Special Elite for headings): same treatment as the
  playground + event pages.
- Landing hero with the criminal-ring pitch copy (see the design doc's
  one-liner) in `NoirHeading` + `NoirCaption` narrator voice.
- Event list as `NoirPanel` cards: status via `NoirDot` + letter-spaced
  label (not pastel `<Badge>`), event dates in typewriter mono, big
  display type for event names.
- CTAs get noir treatment: gold "Create event" button (event runners),
  outlined "Playground" secondary button. No purple/teal Chakra
  `colorScheme`.
- Empty state deserves flavor copy: something like _"No jobs on the
  street tonight. Someone's got to make the first move."_
- Recent activity teaser (couple of feed items from the most recent
  active event) if there's room: brings the drama forward to the
  landing.

**Direction: create page (`/skulduggery/create`):**

- Take the battleship setup UX as reference, NOT the current bare-form
  approach:
  - `client/src/pages/battleship/BattleshipCreatePage.jsx`: the
    base-event form (name, dates, password, tuning knobs): sectioned
    w/ helper text under each field.
  - `client/src/pages/battleship/BattleshipAdminPage.jsx` (long: but
    look at `TeamSection`, `RefsSection`, `VoteThresholdEditor`): the
    canonical pattern for adding teams + refs, editing discord channel
    IDs per team, sending discord test messages, WOM team-name bulk
    edits, etc. Coordinators live here after launch: the shape of
    the sections + how mutations are grouped is worth copying.
- Skulduggery-specific setup fields (all in one sectioned page):
  - **Base event.** Name, start/end datetime, `H` value (multiple of
    10, w/ helper text explaining "base heist-easy payout: anchors
    the whole price ladder"), seed (default random, allow override),
    contract batch size, visible slots.
  - **Kingpin gating.** `kingpinGateCount` knob w/ helper text.
  - **Staff.** Site-admin roster (co-admins), refs: same pattern as
    battleship's `RefsSection` (discord ID input + AddIcon list w/
    remove buttons + Discord test button per ref).
  - **Crews.** Each crew is a card w/:
    - `crewName` input (required)
    - Crew color swatch (small palette picker: noir-adjacent
      accents, not full rainbow)
    - Member Discord IDs (chips or list w/ AddIcon, matches
      battleship's per-team editor)
    - Crew Discord channel ID (for per-crew announcements)
    - Crew Discord role ID (for @mentions on shakedown / heat)
    - WOM team name (for auto-sync: same as battleship)
  - **Content selections.** Filter which registry entries + metric
    types are eligible for contracts (mirrors battleship's
    contentSelections shape). Probably a compact accordion so it
    doesn't dominate: most events use defaults.
  - **Discord.** Announcements channel ID (event-level feed), event
    role for pings.
  - **Launch.** Big gold "Create + Launch" button; a smaller "Save as
    draft" if we want the two-phase flow (create in SETUP → tune →
    launch separately). Match battleship's flow: creating an event
    doesn't have to auto-launch it.
- Every section is a `NoirPanel` w/ a `NoirHeading size="md"` header
  and a small italic Georgia caption underneath explaining what the
  section is for. That gives the runner narrative confidence: "I know
  what I'm about to change."
- Inline validation as they type (H not multiple of 10, missing crew
  members, etc): matches battleship's inline error surfacing.
- **This becomes the "admin page" too**: same page in edit mode after
  the event exists, or a separate `/skulduggery/:eventId/admin` route
  that reuses the same section components. Battleship does the latter;
  probably the right call for us too.

**Direction: team setup UX specifically (bumped, most-detailed ask):**

The event-runner-facing team panel is the single biggest coordinator
surface. Reference `TeamSection` at
`client/src/pages/battleship/BattleshipAdminPage.jsx:275` for the exact
shape:

- Each crew is its own `NoirPanel`: collapsible if needed
- Discord member IDs as chips w/ conflict detection (battleship warns
  when the same Discord ID is on two teams: we should copy that
  invariant)
- Per-crew Discord channel + role fields w/ "test message" buttons
- WOM team name field w/ "sync now" test button
- Delete / archive crew action w/ confirmation modal
- Add-crew CTA sits at the bottom in a dashed noir outline placeholder
  (`+ Add crew`)

The refs section deserves the same design language: `NoirPanel` w/
discord ID chips, per-ref Discord test button, add + remove flow.

### Interaction pattern: Discord is the source of truth

Every state-changing player action (pulling a contract, buying market
items, submitting proof, burning) fires from a Discord slash command,
NOT from a browser click. UI Buy / Pull / Submit buttons open a modal
containing the exact command to post: they never mutate directly.

Reasons (lemon-locked):

- Auditable. Every purchase leaves a channel record everyone can see.
- Multi-source. Refs already work from Discord for proof review;
  keeping player actions there too means one flow, not two.
- Live sync. Server processes → `SKULDUGGERY_MARKET_APPLIED` /
  `SKULDUGGERY_JOB_BOARD_UPDATED` / `SKULDUGGERY_EVENT_FEED_APPENDED`
  push to every subscribed browser. All crews see cut balances, board
  changes, and feed items update instantly: no "who did that" ghosts.

Implementation shape (in-progress):

- Playground `MarketBuyModal` demonstrates the pattern for market
  purchases. Same pattern should apply on the real player event page
  next pass: replace the existing direct mutation calls on the market
  buttons with modal-shown commands. Same for contract pull (currently
  a direct button) once we're comfortable.

### Open placement question: burning a contract

The **Burn** action used to sit in the contract details modal next to
submission commands, which framed it as a routine option. It's not: it's a last-resort escape hatch, one-shot per event, and surfacing it
alongside "submit proof" made it feel like an inline choice a crew
might casually reach for. Pulled it from the details modal for now.

Burn now lives inside the Black Market tab in a separate "Escape hatch"
section. It is executable via Discord (`!skulduggery burn`); the browser
surfaces the consequences and exact command through a command-copy modal
rather than a direct mutation button.

### Copy alignment notes (server truth vs. player-facing copy)

- **Alibi is now reactive**, not banked. Crew must have been Rat Out'd
  during their current contract to buy Alibi; the purchase restores
  the cancelled Insurance/Stakeout buff (`cancelledAt = null`,
  `chargesRemaining = 1`) and flags the Rat Out purchase as
  `ALIBI_FIZZLED` with a `reversed by alibi purchase <id>` note. Old
  banked-alibi paths (pre-emptive fizzling of Heat/Shakedown via
  `recordOffensiveAlibiFizzle`, and Rat Out's `consumeAlibiIfPresent`
  check) have been removed. Heat/Shakedown always land now; only
  Rat Out is reversible, and only via reactive Alibi. Still one-shot
  per event, still costs a def/emp slot. `ALIBI_FIZZLED` enum value
  reused (same semantic, just fires post-hoc); no migration needed.
- **Getaway driver** applies immediately (25% target cut on the current
  unlocked step): earlier scoping copy called it a 60%-progress
  auto-complete, that was wrong. Playground copy now matches server.
- **Inside man** targets the _current_ active contract, not the next
  one: server was correct all along, playground copy has been
  aligned.

## Mission

Implement Skulduggery end to end as a first-class event mode without creating a parallel architecture for systems the repository already has.

The finished feature must:

- generate contracts from the existing server-side content registry;
- use deterministic seeded generation and honor `contentSelections`;
- preserve the canonical submission and referee lifecycle;
- enforce progression, ledger, market, attack, burn, and settlement invariants on the server;
- use database transactions and row locks for contested mutations;
- derive the acting crew from authenticated identity rather than trusting client input;
- publish live updates only after authoritative state has been persisted;
- recover from missed subscription messages by refetching when the browser regains visibility;
- provide player, referee, admin, spectator, and completed-event experiences;
- include migrations, models, GraphQL types/resolvers/operations, pages, reusable UI, feature gating, tests, and operational documentation;
- ship in tested vertical slices, with the v1 slice in the product specification working before post-playtest actions are added.

Do not consider the task complete because the schema compiles or the main page renders. Completion means the lifecycle works through event creation, contract generation, team play, submissions, referee review, payouts, market actions, settlement, and the final leaderboard, including failure and concurrency cases.

## 3. Domain invariants: encode these once, test them everywhere

Create focused domain helpers rather than duplicating conditions across resolvers and components. The server owns all decisions; the client may mirror rules only for display and disabled states.

### Event lifecycle

- `SETUP`: configuration, content selection, staff, crews, and generation preview may change. No gameplay mutations.
- `ACTIVE`: contracts may be pulled and progressed; submissions and market purchases are accepted.
- `SETTLING`: no new pulls, progress, submissions, or purchases. Pre-`endDate` pending submissions remain reviewable. Eligible completions, races, payouts, and audits may settle.
- `COMPLETE`: gameplay is immutable. Queries, feed, audit, summary, and final leaderboard remain readable.
- Scheduled transitions must be idempotent. Running the scheduler twice must not generate a second board, pay twice, or complete twice.

Create a reusable guard such as `requireEventStatus(event, allowedStatuses)` and use it in every mutation.

### Crew identity and permissions

- Derive the player from `context.user`.
- Resolve the crew using the authenticated user's Discord identity and event membership.
- Never accept `crewId`, `submittedBy`, ledger owner, buyer, or actor as authoritative client input.
- Event creators/admins/refs may receive explicitly documented staff powers, but site-admin bypasses must be intentional and tested.
- A regular crew member must not mutate another crew, submit as another player, inspect private tip-off data, or buy with another crew's balance.
- Queries accepting an ID must still authorize access to private fields. An ID is not authorization.

### Contracts and steps

- A crew has zero or one `ACTIVE` contract.
- A board contract is pulled once. Simultaneous pull attempts yield one winner.
- Only the first incomplete step is unlocked; later steps remain locked.
- A step supports multiple submission rows.
- Approving or denying a submission never completes the step.
- Only the authoritative completion mutation changes a step to `COMPLETE` and unlocks the next step.
- Completing the true final step pays the contract exactly once.
- Heat may append a new final step only while the old final step has no pending completion claim.
- Derived values such as `finalStepSubmitted` must not drift. Prefer deriving them from the current final step and pending submissions; if persisted for locking/performance, update and test them in the same transaction as submission/review/heat changes.
- Burned submissions remain immutable audit history; do not delete them.

### Money and audit

- Store monetary amounts as integers.
- Validate `H` is a positive multiple of 10 at creation and update time.
- Contract earnings increase both `cutEarned` and `cutBalance` by the credited share.
- Market spending decreases `cutBalance`, increases `cutSpent`, and never decreases `cutEarned`.
- Refunds increase `cutBalance` and write an explicit compensating ledger entry. Define whether refunds reduce `cutSpent`; use one convention consistently and expose it clearly.
- No balance may become negative unless the product specification is explicitly changed to allow debt.
- Every delta has one immutable ledger/audit row with event, crew, amount, reason/type, related contract/action, actor, and timestamp.
- Payout, refund, purchase, and void handlers must be idempotent. Persist resolution markers or unique source keys so retries cannot double-apply money.

Do not compute `cutSpent` only as `cutEarned - cutBalance`; shakedown splits, refunds, burns, and admin corrections make an explicit audited counter safer.

### Action budgets and market rules

- Each pulled contract has one offensive/territorial slot and one defensive/empowerment slot.
- Slots belong to that contract and do not stockpile.
- Reputation bought between contracts pre-spends the next contract's defensive/empowerment slot.
- Burn does not consume a normal action slot and is limited to one use per crew per event.
- Check price, slot, one-shot usage, target, shields, lifetime caps, event status, and contract status inside the same transaction that applies the purchase.
- A failed validation spends nothing.
- An alibi fizzle is not failed validation: it intentionally spends the attacker's money and slot, consumes the alibi, records the purchase, and applies no attack effect.
- Insurance blocks heat according to the exact current design rule.
- A contract receives at most one lifetime shakedown and at most one heat.
- The acting crew cannot target itself unless a specific action is explicitly self-targeting.

### Shakedown races

- Capture the attacker's metric baseline at purchase time.
- Eligible race timestamps must be at or after `Shakedown.startedAt`.
- WOM-backed completion uses the repository-supported authoritative snapshot timestamp, never an invented precision the WOM response does not provide.
- Manual proof uses immutable server-recorded submission time, subject to eventual approval.
- Ref approval order does not determine the winner.
- If an earlier candidate is denied, evaluate the next eligible approved candidate.
- Do not resolve a winner while an earlier opposing candidate remains pending; retain candidate claims until enough reviews exist to decide correctly.
- Keep the lifetime shakedown attached after race resolution so another crew cannot add a second claim.
- Decrement the attacker's unresolved-race count exactly once on every terminal outcome.
- A burned victim contract creates no score or skim; refund the shakedown fee to spendable balance according to the design and retain audit/feed history.
- Settlement must adjudicate all pre-deadline candidates before declaring an unresolved race lost.

### Shared board and seeded generation

- The persisted board/deck order is authoritative. Never regenerate it during an ordinary query.
- Generation must be deterministic for `(event seed, batch number, content selections, tuning inputs)`.
- Pull, stakeout, discard, replacement draw, and deck exhaustion are contested writes and require locking.
- Enforce the visible-board size and the minimum non-kingpin density.
- Redact kingpin details for ineligible viewers without changing the shared slot identity/order.
- Do not leak redacted details through nested GraphQL fields, tip-off data, feed copy, subscriptions, or errors.
- Deck exhaustion increments the batch/seed generation counter once and appends a deterministic new batch.

## 4. Contract generation from `contentRegistry`

Do this before building UI. The generator is a core domain boundary and should be independently testable.

### Source of truth

Import from `server/utils/contentRegistry.js`:

```js
const { registry } = require('../contentRegistry');
```

Use `registry.BOSSES`, `registry.RAIDS`, `registry.SKILLS`, `registry.MINIGAMES`, and `registry.CLUES`. Do not copy registry entries into a Skulduggery constants file and do not scrape the client API.

Use registry fields where applicable:

- `id` as the stable event content identifier;
- `displayName` for display;
- `enabled` to exclude disabled content;
- `womKey` for WOM-backed metrics;
- `quantities.short|medium|long` for length-driven targets;
- `dropQuantities` and `drops` for unique/item tasks;
- tags or explicit event-specific metadata for eligibility where available.

The registry's existing `category` fields are not automatically Skulduggery's `EASY|INTERMEDIATE|HARD`. Create one explicit, reviewed event-specific classification layer that references registry IDs. Keep it small and auditable. Validate at startup/test time that every configured ID exists, is enabled, has the required quantity bucket, and supports the proposed metric.

Do not mutate registry objects. Persist a resolved snapshot on each generated step-content ID, display label, metric type/unit/target, WOM key, acceptable drops, difficulty, length bucket, and any narrative role/phase-so a later registry edit does not rewrite an event already in progress.

### Suggested pure helpers

Keep deterministic functions in `server/utils/skulduggery/`, for example:

- `buildSkulduggeryContentPool({ registry, contentSelections, difficulty })`
- `resolveRegistryTask(entry, { length, metricType, rng })`
- `generateContractBatch({ seed, batchNumber, boardConfig, contentSelections })`
- `drawReplacementContract(state)`
- `generateShakedownTask({ seed, difficulty, excludedIds })`
- `calculateContractPayout({ hValue, length, difficulty, calibration })`
- `calculateMarketPrice({ hValue, actionType, targetLength })`

Use `seedrandom` and a Fisher–Yates shuffle/range approach consistent with `server/utils/championForge/cfTaskSampler.js`. Never use `Math.random()` for content selection, deck ordering, target quantity, heat selection, or shakedown selection once the event seed exists.

IDs do not need to be deterministic unless the design depends on replaying them, but generated content and ordering must be.

### Filtering order

Apply filters in a predictable order:

1. registry collection is supported;
2. entry is enabled;
3. `contentSelections` does not disable the content ID or metric type;
4. entry is classified for the requested difficulty;
5. requested length quantity range exists;
6. requested metric has required metadata (`womKey`, drops, target range, etc.);
7. contract-local duplicate exclusions;
8. special exclusions required by the design.

Fail event setup with an actionable validation error if a requested pool cannot produce enough distinct steps. Do not silently weaken difficulty, ignore content selections, insert undefined targets, or loop forever trying to find a unique entry.

### Shakedown task pool

The dedicated Skulduggery task pool may live beside the registry extension patterns, but it must still be validated and deterministic. For each task test:

- unique stable ID;
- supported difficulty;
- metric type and unit;
- positive short target;
- WOM key validity when auto-sync is claimed;
- proof requirements when WOM is unavailable;
- baseline compatibility;
- no task can be completed from progress predating the purchase.

### Generator tests

Write pure Jest tests before resolver integration. Cover:

- identical inputs produce byte-for-byte equivalent generated content/order;
- different batch numbers change the deterministic batch;
- disabled registry entries never appear;
- every `contentSelections` category and metric-type filter is honored;
- length selects the correct quantity bucket;
- difficulty selects only its classified pool;
- targets remain within configured ranges;
- contract steps are distinct where required;
- heat uses short quantity and matching difficulty;
- kingpin density never exceeds the board limit;
- an undersized pool fails clearly;
- deck exhaustion produces exactly one next batch;
- no generated step references a missing registry ID or invalid WOM key.

## 5. Persistence design and migrations

Use normalized tables for contested lifecycle state and durable audit data. JSONB is acceptable for immutable configuration/snapshots, but do not hide ledgers, contract ownership, submission status, market purchases, or race resolution inside one large JSON document that requires unsafe read-modify-write cycles.

At minimum, evaluate tables/models for:

- event;
- crew;
- contract;
- contract step;
- action budget, or equivalent columns tied to the active contract;
- submission;
- market purchase;
- immutable ledger entry;
- feed item;
- shakedown and shakedown job;
- stakeout/active buff if implementing post-v1 actions;
- private tip-off preview if implementing post-v1 actions.

Use names consistent with existing models, such as `SkulduggeryEvent` and explicit table names if needed. Use string IDs with a feature prefix consistent with repository conventions.

### Required constraints and indexes

Prefer database constraints in addition to resolver validation:

- foreign keys with intentional delete behavior;
- unique `(eventId, crew identity/member)` constraints as appropriate;
- one active contract per crew, enforced through a transaction and, where practical, a partial unique index;
- unique step order within a contract;
- unique source/idempotency key for ledger entries;
- unique lifetime shakedown per victim contract;
- indexes for board lookup, active contract lookup, pending submissions, ref queues, event feed ordering, unresolved shakedowns, settlement queries, and crew ledger history;
- non-negative balance and target checks where supported;
- valid status enums matching GraphQL/domain constants.

Migration `down` must drop dependent tables before parent tables and clean up PostgreSQL enum types using the patterns in existing migrations.

### Persisted snapshots and timestamps

Persist server-authored timestamps for:

- contract pull;
- step unlock, submission, completion, and burn;
- purchase creation and resolution;
- race start, candidate claim, win, and payout/refund;
- ledger delta;
- feed entry;
- lifecycle transitions and final settlement.

Never accept these timestamps from a regular client. Store enough immutable task metadata on steps/submissions to explain historical results after registry changes.

## 6. GraphQL and resolver architecture

Add Skulduggery types and operations to `server/schema/typeDefs.js`. Register resolvers in `server/schema/resolvers.js`, following the Battleship aggregator structure instead of adding a monolithic resolver block.

Suggested server organization:

```text
server/schema/resolvers/Skulduggery.js
server/schema/resolvers/SkulduggerySubscriptions.js
server/schema/resolvers/skulduggery/helpers.js
server/schema/resolvers/skulduggery/queries.js
server/schema/resolvers/skulduggery/fieldResolvers.js
server/schema/resolvers/skulduggery/mutations/event.js
server/schema/resolvers/skulduggery/mutations/crews.js
server/schema/resolvers/skulduggery/mutations/contracts.js
server/schema/resolvers/skulduggery/mutations/submissions.js
server/schema/resolvers/skulduggery/mutations/market.js
server/schema/resolvers/skulduggery/mutations/settlement.js
```

### Resolver rules

Every mutation should follow this order:

1. `requireAuth(context)`.
2. Load the event/crew/contract from IDs.
3. Derive actor crew and role from authenticated identity.
4. Start a transaction for any stateful gameplay mutation.
5. Reload and lock all contested rows inside the transaction.
6. Revalidate event status, ownership, balance, action slots, target state, caps, and pending claims inside the lock.
7. Apply all state, audit, ledger, and feed changes atomically.
8. Commit.
9. Publish subscriptions and send best-effort external notifications after commit.
10. Return freshly loaded authoritative state or a typed payload.

Do not publish before commit. Do not call Discord while holding database locks. A Discord failure must not roll back valid gameplay.

### Prefer typed payloads for contested mutations

For operations such as pull and market purchase, a payload can carry the updated contract, crew balance, board replacement, feed item, and resolution outcome without forcing the client to guess what changed. Errors must remain safe and not leak hidden kingpin/tip-off data.

### Field-level privacy

Implement kingpin redaction and private previews server-side. Do not return the full contract and merely hide it with CSS.

The job-board query should derive the viewer from auth and return a viewer-safe shape. Avoid `isKingpinVisibleTo(crewId)` as an authorization mechanism; a client-provided crew ID can at most be a lookup hint, never the source of access.

### Associated events and navigation data

If Skulduggery events should appear in the shared active-event surfaces, update `getAssociatedEvents` in `server/schema/resolvers.js` using the established staff/member lookup pattern. Add any required type resolver registration and ensure completed/settling visibility matches product expectations.

### GraphQL tests

Add coverage that:

- the schema builds;
- every client GraphQL document validates against it;
- nullable/non-null fields match realistic lifecycle states;
- redacted board queries do not leak hidden fields;
- private feeds/previews reject other crews;
- unauthenticated, non-member, member, ref, event admin, and site admin roles receive the intended access.

## 7. Canonical submissions and referee workflow

This is the most important reuse boundary.

### Do not merge approval with completion

Follow the convention documented in `client/src/providers/SubmissionsProvider.jsx`:

```text
LOCKED → UNLOCKED → SUBMITTED → COMPLETE
```

- Create proof: add a `PENDING` submission and leave the step available for additional proof.
- Approve proof: change only the submission to `APPROVED`.
- Deny proof: change only the submission to `DENIED`, record a reason, and allow immediate resubmission.
- Mark complete: the separate ref-only mutation advances the step and triggers progression/reward effects.

Use the shared `TileReviewControls` gate. Add `normalizeSkulduggeryTask(task)` beside the existing normalizers rather than recreating buttons and validation. The completion gate must remain equivalent to:

```text
not already complete
AND at least one approved submission
AND no pending submissions
AND progress >= 100
```

The server must enforce the same gate. Client disabled buttons are not security.

### Submission model requirements

Store at least:

- event ID, crew ID, step ID, and contract ID;
- proof URL/message metadata;
- authenticated submitter identity;
- type (`PRESCREENSHOT` if the mode uses it, otherwise ordinary proof);
- status;
- immutable server `submittedAt`;
- reviewer, review time, denial reason;
- the race candidate context needed for shakedown adjudication.

Regular users cannot spoof submitter IDs or timestamps. Staff proxy submission, if supported, must be explicit and tested.

### Ref queue

Reference Battleship's behavior, but use shared components where practical rather than copying a large page verbatim:

- group submissions by step ID;
- active group: pending submissions or temporarily sticky after review;
- reviewed group: no pending submissions, not completed;
- completed group: authoritative step status is complete;
- order submissions pending, then approved, then denied;
- server returns newest submission first;
- stabilize active group order while a ref is working;
- show contract, crew, step order, target, heat bonus badge, and shakedown race badge;
- support filtering/search appropriate to a high-volume event;
- show a human-readable blocked reason when completion is unavailable.

Both ref and player pages must refetch on window focus or `visibilitychange`. WebSocket delivery is not durable.

### Completion transaction

Marking a step complete must lock the step, contract, and crew, then:

1. verify staff authorization and `ACTIVE` or eligible `SETTLING` state;
2. verify approved proof, no pending proof, and sufficient progress;
3. no-op/reject safely if already complete;
4. set completion timestamp;
5. resolve any shakedown candidate affected by this completion;
6. unlock exactly the next step, if present;
7. otherwise complete the contract and pay exactly once;
8. write ledger/feed/audit rows;
9. clear the crew's active contract and expire its action budget only after payout state is durable;
10. commit, then publish updates.

Test retrying this mutation and racing two refs against the same step.

## 9. Ledger and market engine

Keep market catalog metadata separate from mutation code. A catalog entry should define type, category, price function, allowed target, v1 availability, one-shot/cap rules, and display description. The server still performs action-specific validation.

Create shared helpers such as:

- `getMarketListing({ event, crew, actionType })`
- `validateMarketPurchase(...)`
- `consumeActionBudget(...)`
- `applyLedgerDelta(...)`
- `appendFeedItem(...)`
- `resolveAlibi(...)`

Do not create a giant switch that mixes query shaping, authorization, locking, money, side effects, Discord, and pubsub in one function.

### Generic purchase transaction

Inside one transaction:

1. lock event, buyer crew, buyer active contract/action budget, and target rows;
2. validate event status and authenticated membership;
3. calculate price from persisted `H` and target state, never from a client value;
4. validate balance and slot;
5. validate self-targeting, target lifecycle, final-step claim gate, shields, caps, and one-shots;
6. resolve alibi semantics if applicable;
7. deduct balance/increment spent;
8. consume the appropriate slot;
9. create the purchase and ledger entry;
10. apply the action-specific state change;
11. create public and private feed/notification data;
12. commit and publish.

### V1 action checklist

#### Heat

- Select deterministically from the existing registry pool.
- Match victim contract difficulty.
- Always use the short quantity bucket.
- Exclude content already in the contract.
- Reject if the current final step has a pending completion claim.
- Reject if the contract already has a heat.
- Insert the new final step and preserve valid linear status ordering.
- Atomically race against final completion; loser receives a clear error and no charge.
- Insurance handling matches the current design.

#### Insurance

- Attach to the buyer's active contract with server timestamps.
- Enforce expiry consistently in validation and queries; do not rely only on a background cleanup job.
- Expired insurance cannot block heat.
- Purchase, expiry, rat-out cancellation, and contract completion remain auditable.

#### Shakedown

- Require a valid active victim contract with no pending final claim and no lifetime shakedown.
- Require the attacker to have no unresolved race.
- Generate one short, difficulty-matched task deterministically.
- Capture metric baseline and race start atomically.
- Persist candidate timestamps and statuses; do not infer solely from the latest UI state.
- Split a normally completed payout exactly once using integer floor rounding.
- Keep the lifetime marker after win/loss until contract close.
- On burn, create no skim, refund balance only, terminate counters once, and retain history.
- On settlement, wait for all eligible pre-deadline pending candidates.

#### Reputation

- Enforce the completed-contract visibility threshold.
- Charge once per event.
- If bought during a contract, consume its defensive/empowerment slot.
- If bought between contracts, persist a pending pre-spend marker and apply it exactly once to the next pulled contract, including a kingpin.
- Do not consume the pending marker on a failed pull.

#### Burn contract

- Require an active contract and unused event-level burn.
- Cost is server-calculated `min(cutBalance, basePayout)`.
- Preserve submissions and progress history, but mark the contract mechanically forfeited.
- Void payout.
- Resolve/refund a lifetime shakedown according to the current design without creating `cutEarned`.
- Clear active contract and forfeit action slots.
- Mark the burn used and append audit/feed records.
- Replacement board behavior is irrelevant-the contract left the board when pulled; burning must not silently duplicate it.

### Deferred action checklist

Implement each only after the v1 suite remains green.

#### Stakeout

- Lock an on-board contract, not its lifecycle status.
- Enforce one concurrent stakeout per buyer.
- Treat expiry as inactive even if cleanup has not run.
- Atomically race pull, bribe, expiry, and rat out.

#### Rat out

- Target exactly one existing insurance buff or stakeout lock by ID.
- Verify the target belongs to a rival and remains active.
- Apply alibi semantics to the owning rival crew.
- Clear the associated concurrency counter when canceling a stakeout.

#### Tip-off

- Return only the authenticated crew's next three queued contracts.
- Store the preview against stable contract IDs/batch positions.
- Reconcile previews as contracts flip or are discarded.
- Never expose another crew's preview through GraphQL or subscription payloads.

#### Bribe the fixer

- Lock the target slot and deck cursor.
- Reject a card already pulled/locked if the design disallows bribing locks.
- Mark discarded; do not delete audit history.
- Draw exactly one replacement and handle deck exhaustion deterministically.

#### Alibi

- Enforce one purchase per event.
- Bank one charge.
- On the next offensive action, consume attacker money/slot and victim charge, record the fizzle, and apply no offensive side effect.
- Make simultaneous attacks consume the single charge exactly once.

#### Getaway driver

- Target the current unlocked step before any pending submission.
- Persist original and adjusted targets.
- Apply integer floor/minimum rules explicitly; never produce zero unless permitted.
- Ref UI must display the authoritative adjusted target and the reason.

#### Inside man

- Enforce one use per event.
- Allow only the current `UNLOCKED` step with no pending submission.
- Use the same transactional step-completion pipeline with an explicit system-completion source, while bypassing proof gates intentionally.
- Preserve an audit record explaining why no submission exists.

## 10. Settlement and time boundaries

Implement a settlement service callable by scheduler and admin retry. It must be idempotent.

At `endDate`:

1. atomically transition `ACTIVE → SETTLING` once;
2. freeze new gameplay writes;
3. retain submissions whose immutable server `submittedAt <= endDate`;
4. reject proof received after the deadline;
5. allow refs to approve/deny eligible pending proof;
6. resolve contract completions and shakedown races using eligible timestamps;
7. define/administer timeout handling for abandoned pending reviews;
8. ensure all earned payouts, refunds, counters, and feed entries are durable;
9. compute final rankings and honorable mentions from authoritative audit data;
10. transition `SETTLING → COMPLETE` only when no eligible unresolved work remains.

Tests must cover:

- submission one millisecond before versus after deadline;
- approval after deadline of eligible proof;
- earlier pending opposing race claim;
- denied earlier claim causing the later valid claim to win;
- scheduler retry;
- manual settlement retry;
- no double payouts;
- unresolved race with no eligible claim;
- exact leaderboard tie behavior;
- read-only completed event.

Use a controllable clock in domain helpers/tests. Do not scatter `new Date()` calls where time cannot be injected.
